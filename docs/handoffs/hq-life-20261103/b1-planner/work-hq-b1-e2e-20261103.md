## Decisions and why

- **Helper contract.** Scratch is `mkdtemp(join(os.tmpdir(), 'hq-planner-'))`. A caller-supplied `root` must resolve
  under the OS temp directory (checked against both `tmpdir()` and its realpath) and is then owned by the helper:
  `dispose()` removes it. This keeps the "never the checkout" rule enforceable. The service directory comes from
  `import.meta.url`, not `process.cwd()`. `stop()` is SIGTERM, then SIGKILL after 2 s. A `process.once('exit')` hook
  SIGKILLs any Planner still running if the test process dies. A failed first start removes its own root and rejects with
  the child's stderr.
- **No extra helper members.** "Fresh empty data file at the same port" is done in the test by `stop()`, deleting the
  `planning.sqlite3*` files in `target.root` (`wipe()`), then `start()`. The brief fixed the helper's interface, so I did
  not add a `reset()`. Later phases that need it a lot may want one.
- **One Planner per test**, always disposed in a single `afterEach` that also removes each client's user-data directory.
  This costs a Python start per test (expected a few hundred ms each; unmeasured).
- **Real stack, one injected fault point.** Each client is `openServiceConfig(<tmp userData>)` + `config.set({ domain:
  'work', baseUrl })` + `createServices(config, transport)` + `createPlannerLive(bridgeTransport({ call: services.work }))`
  + `createWorkStore(live.port, { recovery: live.recovery })`. The transport wraps `sendHttp` and can drop one matching
  call: `lose('request', …)` answers `unknown` without sending (lost before the Planner), `lose('answer', …)` sends it
  and then answers `unknown` (lost after the Planner applied it). Every exchange is logged with its response so tests
  assert what the Planner really answered (for example the 400 below).
- **Read-backs bypass HQ.** `raw()` is a plain `node:http` request with `agent: false` (no keep-alive pool, so a restarted
  Planner cannot hit a stale socket). Each effect is checked against the service's own `/api/state` and history, not only
  against the store.
- **Second client** is a second full `connect()` (its own `createServices`), as the brief preferred.
- **Today's behaviour asserted for the empty-store restart.** The Planner answers the replay lookup 400 `invalid`
  (`sent_after_version` above its version); the adapter maps any non-409/422 lookup failure to `unavailable` (G7). The
  test therefore asserts: Check returns `stopped`, `save` is `{ kind: 'offline' }`, the entry stays `unconfirmed` with no
  `recovery`, no resend is sent, and the new store stays empty. The lead's `store_changed` reason will change this
  assertion; it is commented in the test.
- **Second Apply.** After a successful Apply the store no longer tracks the write, so `retryUnconfirmed` returns
  `missing`; the test also calls `live.recovery.apply` directly and expects a read-only `replayed` answer, with the
  resend count still 1. The case where the store itself answers `refused` is the extra "Apply answer lost" test.

## Findings

- **Likely defect, not yet tested: a store swapped to an older state is never adopted.** `store.refresh()` returns early
  when `snapshot.stateVersion < state.confirmed.stateVersion`, so after the Planner is replaced by an empty store,
  `poll()` finds a different version, "refreshes", discards the snapshot and leaves the old board showing items that no
  longer exist. Worth a test (possibly `it.fails`) once the `store_changed` design is settled.

  behaviour, not marked `it.fails`.
