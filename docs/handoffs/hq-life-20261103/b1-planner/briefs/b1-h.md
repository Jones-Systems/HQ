## Tasks

1. **Wire.** `decodeVersion` also returns `api` (a positive integer, or absent/null when the body has no `api`) and
   `retention` (`{max, evictedThroughVersion}` from `request_retention`, or null when absent). A present but malformed
   `api` or `request_retention` makes the body malformed, like a malformed `state_version`. `decodeSnapshot` sets
   `Snapshot.api` when `GET /api/state` carries `api` (check the state exchanges; leave it absent otherwise).
2. **Failure reasons in the adapter.** Every `unavailable` the adapter produces carries a reason:
   - transport failure (`{ok:false, kind:'unavailable'}`) on any route: `unreachable`;
   - HTTP 403 or 421 on any route: `refused` (writes keep `noEffect: true`);
   - HTTP 5xx on a read (`state`, `version`, `item`, `history`): `server_error`;
   - any other non-2xx status, or a malformed 2xx body, on `state` or `version`: `incompatible`.
   Writes keep their current classification otherwise (a 5xx or malformed answer to a write is still `unknown`; never
   turn a possibly applied write into `unavailable`). Replay lookups that are answered non-2xx today become
   `unavailable` (G7): keep that only for transport loss, 403/421 (`refused`) and 5xx (`server_error`).
3. **G7: a replay baseline newer than the store.** When the replay route answers 400 because `sent_after_version` is
   greater than the store's current version (see `replay_request` in `services/planner/planning/store.py`), the
   result is `replay_indeterminate` with reason `store_changed`, for both check and apply, and nothing else is sent.
   Detect it robustly: on a replay 400, read `GET /api/version` once and treat it as `store_changed` when the current
   `state_version` is below the recorded `sentAfterVersion`; otherwise keep today's mapping for that 400. Apply's
   authorization rules in the ledger are unchanged (an apply needs a fresh `not_applied` check).
4. **Probe.** New `modules/work/live/health.ts` exporting `probePlanner(transport, now = () => new Date()):
   Promise<PlannerHealth>`. It reads only `GET /api/version` through the transport (never writes, never replays) and
   maps: transport failure → `unavailable/unreachable`; 403/421 → `refused`; 5xx → `server_error`; other non-2xx or a
   malformed body → `incompatible`; each with `httpStatus` when a status was received. A 2xx with a valid body →
   `ready` when `requests.replay` and `hq-references-v1` are both advertised, else `limited`; `limits` lists the
   missing ones in the order `no_replay`, `no_hq_references`, `no_batch` (`items.batch_create`). `api` is the decoded
   value or null. Export it from `modules/work/live/index.ts`, and add `health(): Promise<PlannerHealth>` to
   `PlannerLive` (it calls `probePlanner` with the adapter's transport). `health` is not a `PlannerPort` member: the
   port key set is asserted by test and must not change.
5. **Settings.** "Check connection" for Work uses `probePlanner(window.hqServices.work)` instead of the raw `version`
   call, and shows the result through a new `plannerHealthStatus(health: PlannerHealth): SourceStatus` in
   `data-source-status.ts`:
   - `ready` → `Reachable · Planner API N` (or `Reachable` when `api` is null), tone `good`;
   - `limited` → `Reachable · limited (…)` naming what is missing in plain words (`no replay`, `no HQ links`,
     `no batch create`), tone `neutral`;
   - `refused` → `Refused · start the Planner with --allowed-host for this address`, tone `bad`;
   - `unreachable` → `Unreachable`, tone `bad` (unchanged text);
   - `server_error` → `Planner error`, tone `bad`; `incompatible` → `Not a compatible Planner`, tone `bad`.
   Social's check is unchanged. Keep the 10 s timeout and the generation guard behaviour exactly as they are.
