## Contract (additive; existing fields and outcomes keep their meaning)

```ts
// store.ts
export type ConnectionState =
  | { status: 'connecting' }
  | { status: 'online'; checkedAt: string; limits: PlannerLimit[] }
  | { status: 'offline'; since: string; checkedAt: string; reason: UnavailableReason };

export interface QueuedWrite {
  queueId: string;            // unique across restarts (a UUID), never a per-session counter
  requestId: string;          // the ID of its latest send, or the one reserved for its first send; never reused once sent
  write: WriteOp;             // patch | move | setArchived | markReviewed | updateSettings; never create
  /**
   * What the user saw when making the edit: the projected item (taken before this write itself is projected), or the
   * settings. The compare-and-swap base.
   */
  base: Item | Settings;
  queuedAt: string;
  state: 'queued' | 'sending' | 'conflict' | 'rejected';
  conflict?: { fields: string[]; current: Item | null; settings?: Settings };   // state 'conflict'
  error?: PlannerError;                                                           // state 'rejected'
}

interface WorkState { …; connection: ConnectionState; queued: QueuedWrite[]; durable: 'off' | 'ok' | 'failed' }
type SaveState = … | { kind: 'offline'; queued?: number } | { kind: 'queued'; count: number };
type WriteOutcome<R> = … | { status: 'failed'; error: PlannerError; queued?: { queueId: string } };
interface WorkStoreOptions { …; offlineQueue?: boolean; persistence?: WorkPersistence }

store.flushQueued(): Promise<void>;
store.resolveQueued(queueId: string, choice: 'keep_mine' | 'discard'): Promise<WriteOutcome | WriteOutcome<SettingsResult> | null>;
store.discardQueued(queueId: string): void;
export const QUEUE_LIMIT = 200;
export const DURABLE_SCOPE_NOTE: string;   // e.g. "Queued and unconfirmed changes are kept on this device until resolved."
```

`save` precedence: `offline` (with `queued` only when the count is above zero) before `unconfirmed`, then `queued`,
`saving`, `saved`, `idle`. The count covers every queued entry in any state. `saveLabel` adds
`Offline · N queued` and `N queued`; the existing labels are unchanged. With the queue disabled the store must behave
exactly as today: every existing test passes unmodified, and `save` never carries `queued`.

## Behaviour

**Connection.** `connecting` until the first read answers. Any successful read or write makes it `online`
(`limits` from the confirmed snapshot's features: `no_replay` without `requests.replay`, `no_hq_references` without
`hq-references-v1`, `no_batch` without `items.batch_create`, in that order). A failed read, or a write or Check that
fails `unavailable`, makes it `offline` with the error's `reason` (`unreachable` when absent; a read that fails with any
other Planner error is `incompatible`); `since` stays at the first failure until the store is online again. The
existing private `offline` flag must agree with it.

**When the queue is on.** `options.offlineQueue === true`, or a persistence is in effect (below). The example Planner
and existing tests do not set either, so they never queue.

**Queueing.** For patch, move, setArchived, markReviewed and updateSettings (never create; never an undo's write):
- if the connection is `offline`, queue it without sending;
- if its target (item ID, or `settings`) already has entries in `queued`, queue it behind them without sending, so
  per-target order holds even while online;
- otherwise send as today, and if the send fails `unavailable` (known not delivered), queue it instead of failing.
The outcome of a queued write is `{ status: 'failed', error: { kind: 'unavailable', reason }, queued: { queueId } }`
(reason from the connection, `unreachable` when online). Queued and sending entries are projected on `items`
(after unconfirmed writes, before pending ones); conflict and rejected entries are not projected, so the board shows the
Planner's version there. No undo entry is created for a queued write. Undo refuses, without sending, while its item
has queued entries (`Not undone: this item has changes queued on this device.`). When the queue holds
`QUEUE_LIMIT` entries, a new write fails as today with a danger notice saying it was not kept. Notify once per offline
period that changes are being kept on this device, not once per write (notices are capped at 10).

**Flushing.** `flushQueued()` is single-flight. It first refreshes the snapshot; if that fails, it stops (still
offline). It then sends, one at a time and in queue order, the head entry of each target whose head is `queued`
(a target whose head is `conflict` or `rejected` is blocked until resolved). Each send runs inside the target's
existing `serial` chain. Before sending, compare and swap against the current confirmed item or settings, field by
field, three ways (base, mine, current):
- **patch**: for each patched field, a conflict only if the Planner changed it from `base` and to a value other than
  mine (use the store's `sameValue`/`writable` comparisons). If every patched field already equals mine, drop the
  entry as done. Otherwise rebase onto the current revision and send.
- **move**: a conflict if the Planner changed the status from `base` to one other than my target, or archived or
  restored it; otherwise rebase and send (the anchor stays as recorded).
- **setArchived**: drop as done if the item is already in the wanted state; otherwise rebase and send.
- **markReviewed**: rebase and send.
- **updateSettings**: keys I changed from `base` that the Planner also changed to a different value are conflicts;
  otherwise send the current settings with my changed keys applied. If I changed nothing, drop it.
- the item is missing from the snapshot: `rejected` with `{ kind: 'not_found' }`.
A conflict sends nothing: the entry becomes `conflict` with the differing field names (patch field names, `status`,
`archived`, or settings keys), the Planner's current item or settings, and a warning notice naming the item title.
To send: assign a fresh request ID, mark the entry `sending`, request a durable save and wait for it to settle
(success or failure), then send through the ordinary path. Answers:
- saved: remove the entry and absorb the result as `dispatchWrite` does;
- `unknown`: remove the entry and add an unconfirmed write exactly as `settleFailure` does today (with its intent,
  below); it is never re-sent;
- `unavailable`: put it back to `queued` (the sent request ID is never reused), go offline, stop the flush;
- `revision_conflict`: take `error.current` as the confirmed item, re-run the compare and swap once, and send again
  with a new request ID if it passes; otherwise `conflict`;
- `order_conflict`, `invalid`, `not_found`: `rejected` with the error (an order conflict also refreshes);
- `request_id_reused`: hold the store as today.
After a flush that sent anything, one info notice: `Sent N queued change(s).`
Flush runs automatically after the first successful read that ends an offline period, after restore once the
Planner answers, and after `discardQueued` or `resolveQueued` while online. `load()` and `poll()` await a flush they
start, so tests are deterministic.

**Resolving.** `resolveQueued(id, 'discard')` and `discardQueued(id)` remove an entry in `queued`, `conflict` or
`rejected` (never `sending`) and return null. `resolveQueued(id, 'keep_mine')` applies only to `conflict`: it
replaces `base` with the Planner's current item or settings, sets the entry back to `queued`, flushes, and returns
that entry's outcome (or null if it was not sent, for example while offline).

**Durability (new `modules/work/core/durability.ts`).**

```ts
export interface WorkPersistence { load(): Promise<unknown>; save(value: unknown): Promise<void> }
export const DURABLE_SCHEMA = 'hq.work-durable/v1';
/** Production shell: call before the first Work session for `port`; a store created for that port then uses it. */
export function registerWorkDurability(port: PlannerPort, persistence: WorkPersistence): void;
/** A slot the capture lane can adopt later for HQ drafts: the first claimant receives the stored drafts. */
export function durableDrafts(port: PlannerPort): { claim(): Promise<unknown[]>; save(drafts: unknown[]): void } | null;
export function resetWorkDurability(): void;   // test seam
```

`createWorkStore` uses `options.persistence`, else the one registered for its `port`. One hub per persistence object
aggregates every store using it (several HQ projects share one Planner) into one document:
`{ schema, savedAt, queued: [...], unconfirmed: [...], drafts: [...] }`, where each unconfirmed record is the
`UnconfirmedWrite` plus `intent: RecoveryIntent | null` from `recovery.exportIntent?.(requestId)` taken when it
became unconfirmed (keep intents in a private map, not on the public state). The hub:
- loads once; nothing is saved before that load settles;
- gives the stored queued and unconfirmed entries to the first store that claims them (later stores get none);
- saves the whole aggregate after every change to `queued` or `unconfirmed`, coalesced: one save in flight, then one
  more with the latest aggregate if anything changed meanwhile;
- reports `ok` or `failed`; every store mirrors it in `durable` (`off` without persistence). A load that rejects or
  returns an unreadable document (wrong schema or shape) is `failed` and the hub never saves in that session, so it
  never overwrites what it could not read; a load that returns null or undefined starts empty. Malformed individual
  entries are dropped and counted in one warning notice.
On restore the claiming store: keeps `queued`, `conflict` and `rejected` entries as they were; turns `sending` entries
into unconfirmed writes (state `unconfirmed`; the outcome is unknown, and they are never re-queued or re-sent); calls
`recovery.adoptIntent?.(intent)` for each unconfirmed write with an intent (an entry whose intent is missing or not
adopted stays, and a Check will report `no_intent`); and shows one info notice `Restored N change(s) kept on this
device.`. `load()` waits for the restore before its first read; once the Planner answers, queued entries flush.
